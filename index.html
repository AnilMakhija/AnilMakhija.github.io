Engineering deep dive

Enphase Enlighten: iOS architecture for a connected energy platform

Product context

Enphase Enlighten is the mobile companion to Enphase’s connected energy hardware. The app talks to devices directly and to cloud services, and shows live energy data to 50K+ users.

Engineering challenges

Managing several devices over BLE and Wi-Fi, keeping real-time telemetry flowing into the UI, staying useful when connectivity drops, and letting a six-engineer team work in parallel in one codebase.

BLE and device communication

Multi-device management over CoreBluetooth and Wi-Fi, plus OTA firmware delivery. Device handling lives in one actor-isolated manager rather than being spread across view models.

Telemetry data flow

Real-time IoT telemetry uses WebSocket and MQTT transports. Device data is transformed into typed values before it reaches SwiftUI state, as shown in the pipeline above.

Swift Concurrency and actor isolation

Device state is isolated in actors, and peripheral callbacks are bridged into AsyncSequence streams. I used Thread Sanitizer during testing to check for data races in concurrent device operations. I used TaskGroup for parallel multi-device operations in the later SMA work.

Offline-first data management

Core Data is the persistence layer behind an offline-first sync design, so the app keeps working when connectivity is unreliable.

Modularisation with SPM and Tuist

A monolithic codebase was decomposed into 6 SPM feature modules with protocol-based API contracts. Tuist and xcodebuild manage the modular build configuration, so engineers can deliver features in parallel.

Performance and reliability

Resolved O(n²) chart-rendering bottlenecks on screens that consume high-frequency device data.

Security

Keychain storage, biometric authentication, OAuth2/JWT, certificate pinning and AES-256 encryption.

Testing and CI/CD

Test-driven development with XCTest and XCUITest, gated in Jenkins pipelines alongside SwiftLint.

Architecture trade-offs

WebSocket push over REST polling
Live data arrives as it changes instead of on a timer, at the cost of managing connection lifecycle, reconnects and partial syncs.
Core Data over Realm for the offline cache
It keeps the stack native with fewer dependencies and predictable migrations, at the cost of more boilerplate.
Actors over manual queues
Isolation is expressed in the type system rather than by convention, but APIs become asynchronous and re-entrancy needs care.
SPM modules with protocol contracts
Teams can work in parallel with clear boundaries, at the cost of upfront contract design and build configuration.
